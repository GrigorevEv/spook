# Решения (ADR)

Сюда — только решения, от которых зависит код или поведение приложения: выбор фреймворка, модели или библиотеки, устройство частей приложения, ограничения вроде «данные не покидают машину». Порядок работы, скиллы и инструменты разработки сюда не входят.

## Когда записывать

Нужны все три условия:

1. Решение трудно отменить.
2. Его выбрали из реальных вариантов.
3. Без объяснения читатель кода спросит «почему так?».

Решение, которое легко отменить или которое очевидно, не записывай.

## Формат

- Файл `NNNN-slug.md`: номер — следующий после наибольшего, slug — по-английски через дефис.
- Заголовок — само решение: «База — PostgreSQL, а не MongoDB».
- Первый абзац — контекст, решение и почему, в несколько предложений.
- Разделы — только если они что-то дают:
  - `## Рассмотренные варианты` — отвергнутые варианты, если их стоит помнить;
  - `## Последствия` — неочевидные последствия;
  - `## Источники` — источники и исследования из `docs/research/`.

## Связь с исследованиями

- Исследование — факты, ADR — выбор. Замеры и сырые выводы остаются в исследовании, в ADR — вывод и ссылка на исследование в `## Источники`.
- ADR по итогам исследования: в начале статьи исследования назови этот ADR.
- Новые факты противоречат ADR — скажи об этом прямо и предложи новый ADR. Старый не переписывай: первой строкой под заголовком добавь `Заменён ADR-NNNN.`
